浏览器同源策略与CORS解析

字数: 计算中... 阅读时长: 计算中...

同源策略和 CORS 解决的是同一类问题：浏览器里的一段 JS，能不能读另一个站点的数据。同源策略负责”默认不允许”，CORS 负责”服务器可以显式允许”。

同源策略

登录银行网站 https://bank.com 之后，再打开恶意网站 https://evil.com，恶意网站里执行：

请求会自动带上 bank.com 的 Cookie，服务器认为是本人操作，返回账户数据。没有同源策略的话，这段 JS 就能直接读到结果。

同源的判定标准：协议、域名、端口三者完全一致。

对比 URL 差异 结果
https://api.hello.com/forget 域名不同 跨域
http://hello.com/api/login 协议不同 跨域
https://api.hello.com:8080/register 端口不同 跨域
https://hello.com/login 全部相同 同源

跨域请求浏览器会正常发出去，但响应被拦截，JS 读不到内容（控制台报 CORS 错误）。拦的是”读”，不是”发”。受限制的包括：

限制类型 说明 目的
DOM 访问 无法读取跨域 iframe 的内容 防止恶意页面操作其他网站的界面
存储访问 无法读取跨域的 Cookie、LocalStorage 防止窃取登录凭证、本地数据
网络请求 跨域请求的响应被拦截 防止窃取敏感数据

例外：

  • 表单提交：<form action="..."> 可以跨域提交，因为它只是写入，不需要读响应。
  • 资源嵌入：<img>、<script>、<link> 可以加载跨域资源。这些标签只能加载和执行，不能读内容——<script> 能执行跨域 JS（JSONP 就是利用这一点），但读不到源码。

CORS

前后端分离之后，web.example.com 调 api.example.com 是常态，完全禁止跨域读取不现实。CORS 让服务端用一组 Access-Control-* 响应头声明哪些源可以访问，浏览器收到响应后先核对这批头，符合才把响应体交给 JS。

两条基础规则：

  • 默认拒绝：跨域请求必须由服务端明确返回允许的源，浏览器才放行。
  • 可能改数据的请求先预检：浏览器先发 OPTIONS 问服务端，同意了才发真实请求。

简单请求

同时满足以下三条才算简单请求：

  • 方法是 GET、HEAD 或 POST
  • 只带 CORS 安全头（Accept、Accept-Language、Content-Language、Content-Type 等）
  • Content-Type 只能是 application/x-www-form-urlencoded、multipart/form-data 或 text/plain

简单请求不触发预检，直接发出去，但服务端仍然要返回 Access-Control-Allow-Origin，否则响应照样被拦。

简单请求是”先发出去再说”：请求已经到达服务端，可能已经产生了副作用，浏览器只是不让 JS 读响应。CSRF 能成立就是因为这一点——攻击者不需要读响应，只要请求被执行就够了。

非简单请求与预检

有一项不满足简单请求的条件就会触发预检，比如：

  • 方法为 PUT、DELETE、PATCH
  • 带了自定义头（如 X-Auth-Token）
  • Content-Type 是 application/json

预检是浏览器发的 OPTIONS 请求，带上：

  • Access-Control-Request-Method：真实请求要用的方法
  • Access-Control-Request-Headers：真实请求要带的自定义头

服务端回 Access-Control-Allow-Origin、Access-Control-Allow-Methods、Access-Control-Allow-Headers，浏览器逐项核对，全部通过才发真实请求，否则真实请求根本不会发出。这一步主要拦住”可能改数据”的请求在未授权的情况下发出去；简单请求没有这一步，所以预检防不了 CSRF。

非简单请求每次都发 OPTIONS 会多一轮往返，所以有了预检缓存。服务端在预检响应里返回：

浏览器按（源、URL、凭证模式）缓存这次预检结果，缓存期内同样的请求直接发真实请求，不再发 OPTIONS。各浏览器对上限有自己的限制：Chromium 最高 7200 秒，Firefox 最高 86400 秒，写再大也按上限算。

携带凭证的请求

默认情况下，跨域请求不带 Cookie，响应里的 Set-Cookie 也不会被保存。要带凭证必须两头都配置：

  • 前端：fetch 设置 credentials: 'include'（XHR 是 withCredentials = true）
  • 服务端：返回 Access-Control-Allow-Credentials: true，并且 Access-Control-Allow-Origin 必须是具体源，不能是 *

缺一项浏览器就拒绝。

这么设计是为了避免任意网站都能借用户的 Cookie 跨域请求敏感接口。前端要显式声明，服务端要显式同意，两边都点头才放行。

常见配置漏洞

反射 Origin

攻击者在 evil.com 上放一段 fetch，用户访问该页面时，请求带上目标站点的 Cookie，响应头的 Allow-Origin 正好等于 evil.com，浏览器放行，数据被读走。

常见踩法：

  • 完全不做校验，直接反射
  • 用包含/后缀匹配：origin.includes('trusted.com')，可以被 trusted.com.evil.com、evil-trusted.com 绕过
  • 放行了 null：sandbox iframe 和 data: URL 的 Origin 就是 null，攻击者很容易造出来

内网服务暴露

很多内网管理后台、监控面板为了省事配了 Access-Control-Allow-Origin: *，开发者默认”内网的东西外网访问不到”。但攻击者不需要自己访问内网，让受害者的浏览器去访问就行：

  1. 用户在外网打开恶意页面
  2. 页面里 fetch 内网地址，比如 http://192.168.1.10:8080/api/xxx
  3. 用户的浏览器（在公司内网时）能访问到这个地址，内网服务返回 Allow-Origin: *，响应被放行
  4. 数据被读走

这类服务通常根本没有跨域需求，加 * 只是为了”不报错”。

通用防护要点：

  • 白名单写全：协议 + 域名 + 端口，例如 https://web.example.com，不要用通配符
  • 动态反射必须先过白名单，不要无条件回写 Origin
  • 带凭证时只返回具体源，* 和 Allow-Credentials: true 不能同时出现
  • Max-Age 别设太大，策略变更后旧缓存还会生效一段时间
  • 不需要跨域的接口不要配 CORS 头
  • 敏感接口加认证，不要靠网络位置做防护

CSRF 与 CORS 的区别

  1. 攻击载体
    • CSRF：核心攻击逻辑是 HTML 表单（<form>）或标签（<img>）的钓鱼页面
    • CORS：核心攻击逻辑是 JavaScript 脚本（fetch 或 XMLHttpRequest）的钓鱼页面

为什么 CORS 必须是 JS，而不能用 Form 表单？

  • CSRF（表单）：浏览器提交 <form> 后，页面会立即跳转或刷新，你没法在提交后执行额外的 JS 代码去截获服务器的返回包。
  • CORS（JS 脚本）：浏览器执行 fetch 后，JS 处于等待状态。一旦服务器因为配置错误返回了数据，JS 的 .then() 回调函数就能抓住这些数据，然后马上发送给攻击者。
  1. 攻击的结果
    • CSRF：用户在不知情的情况下提交了包含敏感信息的表单，修改了数据，类似于写操作。
    • CORS：用户在不知情的情况下，恶意脚本利用错误配置读取了返回的敏感信息并外传，类似于读操作。
