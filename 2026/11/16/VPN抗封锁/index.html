前言

最近被某个局域网制裁了，必须研究研究

一、VPN封锁技术

VPN 隧道本质上也是在 TCP/IP 上跑，但它会把原始数据包再套一层私有信封，所以哪怕内容全加密，外部仍能看到它的握手形状、包长、时序和连接习惯；把 OpenVPN、WireGuard 简单改到 443 端口，只是换了门牌号，不等于变成 HTTPS，因为真正 HTTPS 有 TLS 握手、证书链、ALPN 协商、HTTP 语义和浏览器式交互，端口和内容不一致反而可能成为分类信号。

因此，针对 VPN 的封锁并不是一步到位，而是从低成本手段开始层层升级的。

先封 IP 和端口，成本低但换地址只能延长发现周期；再用 DPI 不解密只看稳定指纹，比如固定魔数、首包长度、TLS ClientHello 的扩展顺序和密码套件、UDP/TCP 用法、上下行包长和突发节奏，以及“普通协议该有却没有”的行为；然后主动探测可疑服务器，模仿客户端握手或发畸形包，看它怎么响应，所以抗探测原则是未认证请求不暴露身份——首包带合法客户端才有的认证信息，认证失败就静默丢弃，或转交给真实网页，让探测器看到合理 HTTPS 行为，WireGuard 对未认证包静默有利于抗扫描，但它的 UDP 消息尺寸和时序仍不像网页，所以“不能主动握手确认”不等于“不能被流量分类”。

于是有 TLS 伪装：不是“用了 TLS 就完成”，而是让外部看到语法和行为都合理的 TLS 会话，同时做到密码学一致（握手和证书不能是自造怪变体）、指纹一致（ClientHello、扩展顺序、ALPN 要接近真实浏览器）、行为一致（失败、HTTP 回退、包长时序不能长期机器化）；只在外面再套一层 TLS 可能形成 TLS-in-TLS 特征，内外都 TCP 还会双重拥塞控制和重传干扰。

Reality 类设计主要解决证书管理和主动探测：不要求运营者持有伪装域名传统证书，而是借用真实目标站点的 TLS 特征，并用额外认证信息区分合法客户端，未认证连接表现得像访问真实站点，减少探测器拿到独特响应的机会，但它不保证流量统计上完全等同浏览器，目标站选择、客户端指纹、入口 IP 历史、用户规模和流量模式仍会影响可识别性。QUIC/HTTP/3 则是 UDP 上集成 TLS 1.3，支持多路复用和连接迁移，工程上不受 TCP 队头阻塞连带影响、用户态好调拥塞控制、切网可用 Connection ID 维持逻辑连接，并与 HTTP/3 共享部分外观，但 QUIC 版本、传输参数、包长、请求行为和连接目标仍是指纹，UDP 被限制时必须有 TCP/TLS 回退；Hysteria2 这类更强调高丢包高延迟链路上的吞吐，通过自定义拥塞控制、认证和可选 HTTP/3 外观改善体验，解决的是“受损链路可用性+一定程度伪装”，不是消除所有可观察特征。

再往后，单包指纹被加密随机化后，流量分析会从单包转向序列：视频是持续大下行，网页是短突发，固定频率保活可能暴露长期隧道；抵抗统计分类可以填充包长、扰动时序、多路复用、生成掩护流量，但填充和掩护耗带宽、扰动增延迟、过度随机反而不自然，所以不是噪声越多越好，而是在观测能力、性能预算和用户行为之间折中。前置与中继则是隐藏最终入口，让审查方只看到大型云/CDN/普通服务入口，再由中间层转到真实代理服务器；域前置曾利用 TLS SNI 与 HTTP Host 路由差异，但主流云已多限制，现代替代有受支持的 CDN Worker、中继网络、可插拔传输和短生命周期入口，它们把封锁成本从“封一个小服务器”提高到“影响共享基础设施”，但增加对第三方平台的信任、额外一跳延迟和费用、平台规则变化风险、流量和账户被关联的可能，所以不是免费隐身，而是用架构和运营复杂度换封锁成本。

最后为什么没有“永不封锁协议”：抗封锁至少有地址（IP、ASN、域名、证书历史）、协议（握手格式、响应、传输参数）、行为（包长、时序、连接周期）、运营（配置传播、用户规模、支付与域名）四个暴露面，只补一项，其他维度仍能识别；协议代码只是系统一部分，服务器部署模板高度一致、所有节点同端口、客户端版本长期不更新，都会抵消协议设计优势。

因此选择技术时不该问“哪个协议最隐蔽”，而该问：未认证探测会得到什么响应？客户端握手像哪种常见流量、像到哪层？UDP 不可用有没有独立回退？节点暴露后控制面多快能替换并安全下发？协议有没有公开规范、独立实现或安全审查？伪装增加多少延迟、带宽和运维复杂度？这些才区分真正的系统能力和营销标签；未来也不会靠单一专用协议，而会更多借用标准 Web 传输、可编程中继和多路径连接，并用自动化控制面快速换入口，但标准协议提升兼容性不自动保证不可识别，后量子密码也只保护密钥建立，不解决流量指纹。

2.3 统计与探活ip

订阅把节点列成 43 条，看上去是 43 个独立的希望。

按 server:port 聚合成 41 个入口，再把入口按解析出来的 IP 归堆，只剩 9 个 IP。下表 IP、域名均为虚构示例，非真实地址：

IP 入口数 节点数 协议 端口分布
198.51.100.10 10 10 vmess + ws 16616~16648 段
198.51.100.11 9 9 vmess + ws 同上
203.0.113.20 9 9 anytls 1661~1691 段
198.51.100.12 8 8 vmess + ws 同上
192.0.2.30 1 3 hysteria2 1443
192.0.2.31 1 1 hysteria2 1443
192.0.2.32 1 1 hysteria2 1443

前 4 个 IP 就吃掉了 36 个节点。 使用icmp与tcp握手探活，发现所有节点服务端都是活的。

更具体地说，203.0.113.20 一台机器上挂了 9 个端口，如果这个 IP 出事，现象就是 9 条节点同时红。

所以，第一步需要先判断“红”的原因是不是应为局域网直接将节点服务器的ip加入了黑名单

2.4 ip黑名单?

同一个 IP 上，只要有一个通道能通，这个 IP 就没被整体拉黑。

结果：

IP 节点 同 IP 内的对照 IP 黑名单
198.51.100.10 10 vmess Go UA 黑洞 / Chrome UA 101 证伪
198.51.100.11 9 vmess 同上 证伪
198.51.100.12 8 vmess 同上 证伪
4 个 hy2 IP 6 hy2 TCP 全 refused，但 UDP 通道可用（2614ms） 证伪
203.0.113.20 9 anytls 找不到任何能通的通道 无法排除
203.0.113.21 1 anytls TCP 通但 TLS 静默 无法排除

  • Vmess：同一个 IP 上换个 UA 就能拿到 101，说明网关没有把这个 IP 整体丢掉

  • hy2：TCP 探测全是 refused，看着像IP 死了，可 hy2 节点本身跑得出 2614ms 的延迟。所以 refused 只说明它不开 TCP，不说明 IP 被拉黑。这里有个容易搞反的地方：TCP refused 和 IP 被拉黑是两个完全不同的状态

  • anytls：203.0.113.20 的九个端口裸 TCP 全通（105~330ms），但 TLS 一个字节都不回。我在这个 IP 上找不到任何一个能通的通道——443 和 8443 是 refused，应该是服务端没监听，不能算被封的证据；1661 等端口 TCP 通但 TLS 黑洞。所以难以判断

汇总一下分析结果

判定 入口数 节点数 协议
被 GoUA 指纹拦 27 27 vmess + ws（明文，无 TLS）
TLS 被黑洞 10 10 anytls（TCP + TLS）
UDP 协议 4 6 hysteria2（QUIC）

值得注意：这张表的 10 个 anytls 里有 9 个挂在同一个 IP 上，所以它列的不是10 个独立的故障，而是1 个 IP 上的 9 个端口 + 另 1 个 IP。

2.5 分层判断

下面三组证据，分别对应这三层。

第一组：只把 UA 换掉。

入口是 planb.relay-a.example:16617，裸 TCP 通 168ms。我用原始 socket 手拼 WebSocket 升级报文，头部顺序完全照 mihomo 的来，只改 UA：

UA ws 升级结果 mihomo 延迟 API 真实访问 google
Go-http-client/1.1 黑洞（读超时） Timeout 15054ms http=000
Chrome/131（浏览器串） 101 Switching Protocols delay 1683ms http=302

三个 IP 各跑三遍，9/9 次结果一致。同一台服务器、同一个端口、同一个 Host，唯一的变量就是 UA 这一个字段。

第二组：测anytls的tcp+tls连通性

目标 裸 TCP 普通 TLS
203.0.113.20:443 拒绝 Connection refused
203.0.113.20:8443 拒绝 Connection refused
203.0.113.20:1661（anytls 口） 通 105ms 静默黑洞
203.0.113.20:1661 + ALPN h2 通 静默黑洞
smtp.qq.com:465（对照） 通 TLS 成功 TLS_AES_256_GCM_SHA384
www.baidu.com:443（对照） 通 TLS 成功 ECDHE-RSA-AES128-GCM-SHA256

对照组说明这不是本机 TLS 栈坏了也不是非标端口的 TLS 被全局禁掉——smtp.qq.com:465 本身就是非标端口，它握手好好的。

第三组：测hy2的tcp连通性

这组没什么可分析的，6 个节点全拒，因为 hy2 走 UDP/QUIC，压根不监听 TCP。但它恰好是最关键的一组——它证明了网关的 DPI 只处理 TCP。

2.6 Vmess封禁判断

这是这次最反直觉的部分。我一开始也往协议被识别的方向想，直到做了那个只换 UA 的对照才转向。

先排除掉几个常见的怀疑对象。

2.6.1 DNS？

在配置文件提取节点的host，dns查询

这批 vmess 节点的 Host 是 30fa289f13887d772259ba46e50b6afb.mobgslb.tbcache.com——借用淘宝 CDN 的命名空间拼出来的虚构域名，公共 DNS 下返回 NXDOMAIN，换哪个解析器都查不出东西。客户端真正连的是 server 字段（planb.relay-a.example），Host 只是伪装用的。既然 Host 是假的、还照样能拿到 101，说明网关不靠 Host 判断。典型的协议特征伪造

2.6.2 端口？

同一台机器在 16616~16648 这段端口里挂了十个左右节点，全部是Go UA 黑洞、Chrome UA 101，一个例外都没有。

2.6.3 协议？

因为 WS 升级在 Chrome UA 下完整成功连接节点服务器，说明协议栈没问题。

2.6.4 结论

排除完只剩一个结论：网关匹配的是http明文里的UA头，很典型的被动DPI。

2.7 anyTLS封禁判断

2.5 的第二组只留下一个现象：TCP 通，TLS 一个字节都不回。2.4 也因此把这 10 个 anytls 归进了IP 黑名单无法排除。这一节把两件事一起解决。

先复述现象。这一层和 vmess 那层长得像，但触发点完全不同：

目标 裸 TCP 普通 TLS
203.0.113.20:443 拒绝 Connection refused
203.0.113.20:8443 拒绝 Connection refused
203.0.113.20:1661（anytls 口） 通 105ms 静默黑洞
203.0.113.20:1661 + ALPN h2 通 静默黑洞

注意静默这两个字。不是 RST，不是 400，是连接建立之后一个字节都不回，一直挂到超时。这种形态通常意味着中间设备读到了某个字段，然后主动不转发。

接下来按老办法，一个变量一个变量地换。

2.7.1 JA3指纹？

anytls 节点自带 client-fingerprint: chrome 和 alpn: [h2, http/1.1]，mihomo 会真的用 uTLS 把 ClientHello 伪装成 Chrome 的样子。如果封锁是按 TLS 指纹做的，带 Chrome 指纹就该能过。

先把内核日志开到 debug，再打延迟：

日志里明确打出 use specified fingerprint:Chrome，证明指纹真的用上了，然后延迟 API 依然 Timeout。

所以应该不是指纹问题。

2.7.2 SNI域名黑名单？

指纹不是变量，那 ClientHello 里还剩什么可读的？SNI。

先假设某个域名被拉黑，于是把 SNI 换成各种值：

SNI 结果
any.node-a.example（原配置） 超时（零回应）
www.microsoft.com 超时
www.baidu.com 超时
cloud.tencent.com 超时
203.0.113.20（IP 字面量） 超时
不带 SNI 握手成功 TLS_AES_128_GCM_SHA256

换什么都拦，只有没有才放行。所以不是按域名拉黑。

2.7.3 SNI与IP不一致？

还有一种解释：设备在做一致性校验，SNI 解析出来的 IP 和实际连接的目的 IP 对不上就丢。这个假设听上去很合理，因为 anytls 的 sni 和 server 确实不是同一个域名。

于是特意挑两个一致的组合：

目标 SNI 一致性 结果
203.0.113.20:1661 ousua.node-a.example 该域名确实解析到 203.0.113.20 超时
203.0.113.21:1699 hkt2.node-b.example 该域名确实解析到 203.0.113.21 超时

一致的也超时，假设证伪。

2.7.4 变量SNI

前面三个假设都是SNI 的内容有问题。最后把内容这个维度彻底剥离：换一个国内能正常访问的目的地，只改 SNI。

目标 SNI 结果
www.baidu.com:443 不带 握手成功 ECDHE-RSA-AES128-GCM-SHA256
www.baidu.com:443 www.baidu.com 握手成功
www.baidu.com:443 any.node-a.example 超时

同一个目的地、同一台服务器，只因为 SNI 换成了 any.node-a.example 就死。

结论收敛成一句：向这些境外 IP 发起 TLS 时，ClientHello 里只要存在 SNI 扩展且内容不在白名单内，就被静默丢弃；不带 SNI 时设备无法分类，放行。

这也解释了为什么 2.5 里改 client-fingerprint 完全无效——指纹伪装改的是 ClientHello 的结构（字段顺序、扩展集合），SNI 是一个独立字段。两者是正交的维度，很容易被混成一个TLS 伪装的概念。

顺带把 2.4 的悬案结了：203.0.113.20 不是IP 被拉黑，因为不带 SNI 时 TLS 能握手成功，数据确实从那个 IP 上过去了。这个 IP 上的 TLS 不是不能用，是不能带着 SNI 用。

2.7.5 清空SNI？

最直接的想法是把 sni 去掉：

实测结果：香港HK-A -> Timeout
