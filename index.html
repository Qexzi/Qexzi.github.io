VPN抗封锁

post @ 2026-11-16

前言

最近被某个局域网制裁了，必须研究研究

一、VPN封锁技术

VPN 隧道本质上也是在 TCP/IP 上跑，但它会把原始数据包再套一层私有信封，所以哪怕内容全加密，外部仍能看到它的握手形状、包长、时序和连接习惯；把 OpenVPN、WireGuard 简单改到 443 端口，只是换了门牌号，不等于变成 HTTPS，因为真正 HTTPS 有 TLS 握手、证书链、ALPN 协商、HTTP 语义和浏览器式交互，端口和内容不一致反而可能成为分类信号。

因此，针对 VPN 的封锁并不是一步到位，而是从低成本手段开始层层升级的。

先封 IP 和端口，成本低但换地址只能延长发现周期；再用 DPI 不解密只看稳定指纹，比如固定魔数、首包长度、TLS ClientHello 的扩展顺序和密码套件、UDP/TCP 用法、上下行包长和突发节奏，以及“普通协议该有却没有”的行为；然后主动探测可疑服务器，模仿客户端握手或发畸形包，看它怎么响应，所以抗探测原则是未认证请求不暴露身份——首包带合法客户端才有的认证信息，认证失败就静默丢弃，或转交给真实网页，让探测器看到合理 HTTPS 行为，WireGuard 对未认证包静默有利于抗扫描，但它的 UDP 消息尺寸和时序仍不像网页，所以“不能主动握手确认”不等于“不能被流量分类”。

于是有 TLS 伪装：不是“用了 TLS 就完成”，而是让外部看到语法和行为都合理的 TLS 会话，同时做到密码学一致（握手和证书不能是自造怪变体）、指纹一致（ClientHello、扩展顺序、ALPN 要接近真实浏览器）、行为一致（失败、HTTP 回退、包长时序不能长期机器化）；只在外面再套一层 TLS 可能形成 TLS-in-TLS 特征，内外都 TCP 还会双重拥塞控制和重传干扰。

Reality 类设计主要解决证书管理和主动探测：不要求运营者持有伪装域名传统证书，而是借用真实目标站点的 TLS 特征，并用额外认证信息区分合法客户端，未认证连接表现得像访问真实站点，减少探测器拿到独特响应的机会，但它不保证流量统计上完全等同浏览器，目标站选择、客户端指纹、入口 IP 历史、用户规模和流量模式仍会影响可识别性。QUIC/HTTP/3 则是 UDP 上集成 TLS 1.3，支持多路复用和连接迁移，工程上不受 TCP 队头阻塞连带影响、用户态好调拥塞控制、切网可用 Connection ID 维持逻辑连接，并与 HTTP/3 共享部分外观，但 QUIC 版本、传输参数、包长、请求行为和连接目标仍是指纹，UDP 被限制时必须有 TCP/TLS 回退；Hysteria2 这类更强调高丢包高延迟链路上的吞吐，通过自定义拥塞控制、认证和可选 HTTP/3 外观改善体验，解决的是“受损链路可用性+一定程度伪装”，不是消除所有可观察特征。

再往后，单包指纹被加密随机化后，流量分析会从单包转向序列：视频是持续大下行，网页是短突发，固定频率保活可能暴露长期隧道；抵抗统计分类可以填充包长、扰动时序、多路复用、生成掩护流量，但填充和掩护耗带宽、扰动增延迟、过度随机反而不自然，所以不是噪声越多越好，而是在观测能力、性能预算和用户行为之间折中。前置与中继则是隐藏最终入口，让审查方只看到大型云/CDN/普通服务入口，再由中间层转到真实代理服务器；域前置曾利用 TLS SNI 与 HTTP Host 路由差异，但主流云已多限制，现代替代有受支持的 CDN Worker、中继网络、可插拔传输和短生命周期入口，它们把封锁成本从“封一个小服务器”提高到“影响共享基础设施”，但增加对第三方平台的信任、额外一跳延迟和费用、平台规则变化风险、流量和账户被关联的可能，所以不是免费隐身，而是用架构和运营复杂度换封锁成本。

最后为什么没有“永不封锁协议”：抗封锁至少有地址（IP、ASN、域名、证书历史）、协议（握手格式、响应、传输参数）、行为（包长、时序、连接周期）、运营（配置传播、用户规模、支付与域名）四个暴露面，只补一项，其他维度仍能识别；协议代码只是系统一部分，服务器部署模板高度一致、所有节点同端口、客户端版本长期不更新，都会抵消协议设计优势。

一、反射

有一个疑问：反射在原生 Java 里到底是为了处理什么问题？

编译期静态类型系统无法覆盖、但运行时又必须按名字或元数据去操作类和对象”的动态性问题

普通 Java 代码在编译时就必须知道要 new 哪个类、调用哪个方法、访问哪个字段，而反射让程序在运行时才根据类名、方法名、字段名、注解、配置或外部输入，去加载类、获取构造器、创建实例、调用方法、读写字段、检查注解和泛型/继承信息，从而让框架和基础设施代码能够用一套通用逻辑处理任意类型，而不是为每个业务类写死代码。

典型场景包括 Spring 这类容器根据配置实例化 Bean 并注入依赖、JSON/ORM 框架按字段名序列化和映射对象、JUnit 发现并执行带 @Test 的方法、JDBC 通过类名加载驱动、动态代理在方法调用前后织入逻辑、插件系统按字符串加载实现类，以及测试和工具代码访问私有或受保护成员。

它还要处理类加载时机、访问权限、泛型擦除后信息有限、注解保留策略、异常包装、性能开销、安全限制和 Java 模块化下的开放性问题。但反射本身不实现业务逻辑，它只是提供“运行时动态访问类型信息与成员”的能力；能用接口多态、工厂、函数式接口等静态手段解决的地方通常不该用反射，反射主要留给框架、容器、序列化、代理、测试工具这类必须在编译期对未知类型做通用处理的底层代码。
